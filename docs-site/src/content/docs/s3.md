---
title: Amazon S3
description: Read records that already sit in an S3 bucket.
---

Use S3 when the records are already objects in a bucket. You do not export them into another format first. A connection covers one bucket and one prefix, and you pick the mode that matches how much access you want Tacit to have.

All three modes produce the same record as the [push API](/api/). Your team sees one stream of knowledge whether a file was pushed by an app or read from storage.

S3 event notifications name the object. They do not include its bytes. Something still has to read the object: the role you grant Tacit, or the agent you run.

## What an object becomes

Tacit does not ask you to rename files. A dump can be ingested as it is, which is usually what you want for a folder that other systems already write to.

| Field | Value |
| --- | --- |
| `source` | The connection name, for example `s3:finance-exports` |
| `type` | `file` |
| `id` | `{bucket}/{key}` |
| content hash | The S3 version id, or the etag if the bucket is not versioned |
| `seen_at` | The object's `LastModified` |

A new version, or a new etag, on the same key updates that record. A delete marker closes it. It does not create a new id, so a revised export stays attached to the original file.

If the business id should be something other than the object key, place a sidecar next to the object, named `{key}.tacit.json`:

```json
{
  "source": "acme_erp",
  "type": "ticket",
  "id": "T-1042",
  "seen_at": "2026-09-29T18:00:00Z"
}
```

When the sidecar is present, those fields identify the record, and the file can keep the path your other tools expect. When it is absent, the table above applies. You can load a bucket with no sidecars.

Tacit records and skips, without reading the body:

- objects over the agreed size cap
- Glacier and other archived storage classes
- temporary suffixes you list (`.tmp`, partial uploads)
- the prefix Tacit would use for its own markers, if any

The original object is left unchanged. If Tacit needs a text copy of a PDF or a spreadsheet in order to read it, that copy is a separate object. Your file stays as it was.

## Mode A: Tacit reads the bucket

This is the simplest option when you are comfortable letting Tacit read one prefix. You do not copy the corpus into Tacit storage, and you do not run anything in your account.

You create an IAM role. Tacit stores the role ARN, the region, the bucket, the prefix, and an external id that equals the connection id. Tacit does not store access keys.

The role trusts Tacit's account only when the external id matches. That stops another Tacit customer from presenting your role name.

Permissions, limited to the prefix:

- `s3:ListBucket` on that prefix
- `s3:GetObject` on that prefix
- `s3:GetObjectVersion` if the bucket is versioned
- `kms:Decrypt` on your key, if the bucket uses SSE-KMS

The role cannot put or delete objects. Tacit keeps the listing cursor in Tacit, not in your bucket, so the bucket stays a place your other systems own.

The first run lists the prefix and queues one record per object, which is how a folder you already have becomes searchable knowledge. Later runs continue from the cursor (`LastModified`, then key). Tacit reads the object in your bucket at processing time. If the object has been removed by the time Tacit reads it, that record fails and can be retried. It is not silently dropped.

## Mode B: event notifications, plus the same listing

Use this when new files should show up sooner than the next scheduled list. You keep the same read role as Mode A, and you add a notification so Tacit hears about creates and deletes.

You send `s3:ObjectCreated:*` and `s3:ObjectRemoved:*` to a queue Tacit pulls (Amazon SNS or EventBridge into Amazon SQS). Tacit does not offer a public URL that accepts unsigned bucket notifications.

Each message carries the bucket, key, version id, etag, and event name. A worker then reads the object with the role.

Notifications are lost in normal AWS operation, and they do not describe objects that were already in the bucket. The listing from Mode A still runs on a schedule and compares etags, so a missed event is caught on the next pass. The first run is always a full list, even when notifications are on.

## Mode C: lightweight agent

Use this when Tacit should not hold a role in your account, or when your network only allows outbound connections. You keep the bucket credentials on your side. Tacit only receives what the agent sends.

You run a small process in your account. It opens no inbound port. It has list and read permission on the prefix, and it holds an ingest key from the [push API](/api/) (or a short-lived token it fetches over HTTPS).

It lists the prefix, remembers the last key and etag locally, and calls the push API for each new object.

- Pointer. If Tacit also has the Mode A role, the agent sends the bucket, key, version, and etag. Tacit reads the object. The agent is there so a missed event still gets sent.
- Upload. If Tacit cannot read the bucket, the agent uploads the bytes through the artifact URL, then sends the record. The bytes move once, into storage encrypted for your organization.

The agent logs keys, etags, sizes, and statuses. It does not log file contents. The same progress is reported to Tacit, so you can see how far the listing has reached from the product, not only from the machine running the agent.

A later option runs processing inside your account as well, so the derived knowledge stays with you. That option is described below. It is not part of the first agent build. The first agent is a client of the push API.

## What leaves your account

This is the distinction that matters in a security review. The files and the knowledge Tacit writes from them do not have to live in the same place, and you should decide that before rollout.

| Mode | Where the file bytes are read | Where the derived knowledge is written |
| --- | --- | --- |
| A. Role | In your bucket. Tacit reads the object to process it. The bucket is not copied. | In Tacit, for the standard deployment |
| B. Events | Same as Mode A. The notification itself contains no file bytes. | In Tacit, for the standard deployment |
| C. Agent, pointer | Same as Mode A. The agent only sends the pointer. | In Tacit, for the standard deployment |
| C. Agent, upload | Copied once, over TLS, into storage encrypted for your organization | In Tacit, for the standard deployment |
| C. Agent, local processing (later) | Stay in your account | Stay in your account. Tacit receives the stage outcome only |

For Mode A and Mode B, the files stay in your bucket. Claims, entities, and embeddings are still written to Tacit in the standard deployment. "Nothing derived left the account" applies only to the later option that runs processing locally. If that knowledge must remain in your account, say so before rollout. The interface stays the same. The processing location is what changes.
